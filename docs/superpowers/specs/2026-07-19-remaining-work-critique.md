# Critic pass on the remaining-work cycle plan

Fable 5, 2026-07-19. Completeness / correctness / implementer-safety review of the scoped
items before the cycle plan was written. Retained because several findings are load-bearing.

---

## 1. WHAT IS MISSING

**(a) Reachability — the plan has no item for the fact that no target user can open the app.** `.vercel/project.json` shows a Vercel deployment with no custom domain anywhere in the repo, and `vercel.json:6` pins `regions: ["iad1"]`. `*.vercel.app` is not resolvable from mainland China. Every item A–G improves a screen that a Tibetan patient in Qinghai or the TAR cannot load. Item F correctly says 备案 is a distribution-model decision and not engineering, but it stops there — it never states that *today, with no domain bound, the product's delivered value is zero regardless of all seven items*. That belongs in the plan as an explicit, dated, non-engineering blocker with an owner, or the plan is optimising a system with no users.

**(b) The curation cycle — 18 high-stakes entries, NOT started.** `docs/superpowers/specs/2026-07-18-recognition-gap-worklist.md:§2` lists the work that actually drives the headline number: `Lactate`, `Free Calcium`, `pO2`, `pCO2`, `Base Excess`, `Anion Gap`, `Urea Nitrogen`, `Troponin T`, `Bilirubin Total`, `Hematocrit Calculated`, `Calculated Total CO2`, plus `TT`, `PT%`, myoglobin, CK-MB mass. **Item D curates exactly one of them (`PT%`) and pre-registers +1 row.** R6-gold is 62.2% ZH / 42.0% US. Seventeen entries of the eighteen are unscoped. The worklist's own table shows what this costs: Lactate 8.4 mmol/L in sepsis and Troponin T 2.4 ng/mL in a massive MI both render "Above your report's range", `needsConfirm=false`, **no flag at all**. That is the largest live safety gap in the product and the plan allocates one entry to it. Items B, E and G are polish by comparison.

**(c) Error boundaries do not exist.** `app/` has no `error.tsx`, no `global-error.tsx`, no `not-found.tsx`. A throw inside `SummaryView` — which this plan modifies in items A, B and E simultaneously — drops the user to Next's default English stack-trace page. For an app whose entire premise is language access, the failure surface is monolingual and unstyled.

**(d) `app/~offline/page.tsx` is hardcoded English and its copy is factually wrong.** It says saved reports "are still available once you're back online" — but they live in IndexedDB (`lib/db.ts`) and are available *precisely when offline*. Item G found `DisclaimerBanner.tsx` as the un-i18n'd outlier and missed this one, which is worse because it also misinforms. `app/manifest.ts:6-8` (`name`/`description`) is likewise EN-only, so the PWA install prompt is English.

**(e) No language selector exists before the result page — this silently voids Item F Gap 3.** `app/result/page.tsx:53-61` is the only language toggle in the app. `app/page.tsx:9` pins `const [lang] = useState<Lang>('en')` with no setter, and **`CaptureCard` takes no `lang` prop at all** (`app/page.tsx:24` renders `<CaptureCard />` bare). The consent screen at `components/CaptureCard.tsx:528-577` renders EN and ZH side by side via four hardcoded `resolveText(..., 'en')` / `(..., 'zh')` call sites. Item F says "move consent strings into `lib/uiCopy.ts` and render via `LocalizedText`" — done literally, that produces **zero user-visible change**, because there is no `lang` to render in and no way for the user to have chosen `bo` yet. The prerequisite (a language selector at the entry point, threaded into `CaptureCard`, persisted) is in no item.

**(f) Language choice is not persisted.** `app/result/page.tsx:20` `useState<Lang>('en')` is per-mount. Navigate home and back and a Tibetan user is in English again. Every item that adds Tibetan content assumes a durable language preference that does not exist.

**(g) The doctor-notes path is nearly absent from the plan.** `lib/notesGuard.ts` carries 23 of the 36 guard messages (Item G's own count — the *largest* single guard surface), `app/api/translate-notes/route.ts` is a live paid route, and `lib/notesSummary.ts` emits chips. No item audits the notes path for the B1 conditional-referral leak that Item F found in the labs path, and `validation/b1VerdictLeakage.test.ts` does not cover notes copy at all. Notes are free-text *translation* of clinical claims — the one place the "LLM is OCR-only" invariant does not hold — and the plan does not look at it.

**(h) Retention has no mechanism.** `lib/db.ts` opens at version 1 with no expiry and no `deleteAllVisits`. Item F names this (Gap 5) but scopes it as a *disclosure* change; the code change is unscoped.

**(i) No request timeout on the model call.** `app/api/extract/route.ts:32-47` awaits `messages.parse` with no `AbortSignal`. On a censored, high-latency path from Tibet this hangs until the platform kills it and the user sees the generic 502 string at `:53`.

## 2. WHAT IS WRONG

**(1) Items A and E specify two incompatible designs for the same data — this is the most serious defect in the plan.** Item A §3 makes the printed flag **replace the chip** ("Marked high on your report", precedence over the derived position, surviving R13/R16). Item E §2 item 4 adds a **separate `reportFlag` field** rendered under a "Marked on your report" label and explicitly leaves the chip unchanged. Both cite the same absent schema field. If Codex implements both, the flag renders twice with conflicting semantics; if it implements one, the other item's tests contradict. **Pick one before writing the spec.** Item E's is safer (attribution in a labelled field, chip untouched) and Item A's is more useful; they cannot coexist.

**(2) Items A and E also conflict on the `reportRange` gate, and A is a regression against E.** Item E defect #1 says reproduce `printedRange` whenever it is a non-empty string, independent of `defer` (`lib/summary.ts:269`). Item A §3 says change the gate to `(!defer || flagDir !== null)` — which still withholds the printed range on every unparseable-range row that carries no flag. If A lands after E, A narrows E's fix back. The correct target is E's unconditional reproduction; A must not touch that line.

**(3) Items E and G propose different, incompatible fixes to `lib/summary.ts:252-253`, and E's is wrong for English-source reports.** Item E §3 says `zh: reviewed(extracted.name)`, `en: fallback('zh')`. Item G §2b says `unverified()` on all slots. E's version hardcodes the assumption that the OCR'd name is Chinese — but the brief states source languages are **ZH and EN**, and `ExtractedRow` (`lib/types.ts:66-73`) and `GroundedReport` (`:83-88`) carry **no source-language field**. On a MIMIC-style English report, E's fix labels an English analyte name as reviewed Chinese and hands a `bo` user a `zh`-classed CJK-font English string. G's `unverified()` is language-agnostic and correct. Use G's, or add a source-language field first.

**(4) Item B's proposed gate under-polices exactly the strings it exists to catch.** I ran the strict `BANNED` bank (`validation/b1VerdictLeakage.test.ts:44-56`) over all 111 `entry.plain` values: **only 3 hits, all Chinese** — `neutrophil_abs` zh, `urine_ketones` zh, `lactate` zh. The English counterparts do **not** trip it: `neutrophil_abs` EN ends "…needs prompt medical attention" and `urine_ketones` EN "…a warning sign needing prompt attention", but `BANNED` only has `/promptly/i` (the `-ly` is load-bearing) and `/critical range/i`, which does not match lactate's "critical value". So Item B's "gate against `BANNED` only" would go green after fixing three Chinese strings while shipping English triage prose into a newly-rendered glossary. The gate must add `/needs? (urgent|prompt|immediate)/i` and `/critical value/i`, or it certifies the defect it was written to catch.

**(5) Item F option (a) destroys the metric Item D pre-registers against.** `validation/real-corpus/realContentBench.ts:275` computes `r6CoverageGold = goldHighStakesConfirmed / goldHighStakesRows` with the numerator being `row.needsConfirm` (`:221`). Item F option (a) makes `ConfirmValues.tsx:24` list every row and demotes `needsConfirm` to "an internal metric only". At that point "high-stakes rows reaching the confirm gate" no longer describes anything a user experiences — it measures an internal boolean with no rendered correlate. That is structurally the same failure as 80% self-graded / 27.4% gold-graded. Worse, `realContentBench.ts:256` defines the repo's *safety* metric as `classifiedDetail.filter(d => !d.needsConfirm)` — "rows we present confidently". Item F option (b) (moving R3/R11/R17 out of `needsConfirm`) would move critical rows *into* the confident set, inflating the denominator of the agreement metric with the rows most likely to disagree. **Option (b) silently corrupts the safety metric; option (a) makes R6-gold vacuous.** Neither is acceptable without renaming and re-grounding the metric in the same change.

**(6) Item F's F-2a fix is insufficient on its own and the plan should say so.** Removing `classification === 'critical'` from `lib/guard.ts:345` removes the *text* leak, but R3 at `:290` still sets `needsConfirm = true` for critical rows, so the confirm-list membership still varies with the patient's number. F-2a alone closes the visible half of a two-channel leak and would read as "fixed" in a green test run. F-2a and F-2b must land together or the item is misleading.

**(7) Item E's defect #3 fix is incomplete — it names one of two call sites.** Item E says gate the name on `handled` at `lib/summary.ts:249`. But `components/ConfirmValues.tsx:73` independently renders `r.entry.name` on the confirm screen (falling back to `r.extracted.name` at `:91`). An R18 blood-gas row resolving to `urine_ph` shows "Urine pH" on the confirm screen too. Fixing `summary.ts` alone leaves the wrong heading on the screen the user sees *first*.

**(8) Item G's re-baselining analysis is right; the framing in items B and E is wrong.** Item G §3 correctly shows `lib/localizationBaseline.test.ts:99,107,115` parameterises over `['en','zh']` only, so Tibetan never moves the hash. But Item B §5 and Item E §5 both instruct re-baselining `REFERENCE_BASELINE.en/.zh` — correctly, since they edit *English and Chinese* source strings. The plan must state that these are the only two items permitted to move a hash, and that a hash movement in items A, C, D, F or G is a bug, not a chore.

**(9) Stale spec headers will mislead the implementer.** `docs/superpowers/specs/2026-07-19-chinese-coverage.md:3` says "Status: **NOT STARTED**" but the work shipped — the three bucket-A aliases are live (`data/reference-labs.ts:53,959,985`) and the locks exist (`data/english-aliases.test.ts:46-48`), and the spec's baseline of 54.1% (20/37) is superseded by Item D's measured 62.2% (23/37). `docs/superpowers/specs/2026-07-19-urinalysis-coverage.md:3` says the same while commit `7531700` shipped it. An implementer reading these headers will redo shipped work or mis-baseline. Fix the headers as a precondition.

**(10) One negative finding worth recording:** the recognition-gap worklist's §4 "SEPARATE BUG FOUND (not yet fixed)" — the urine β2-microglobulin showing our serum "Typical range" with no caveat — **has been fixed**. `lib/guard.ts:409-430` implements `R17-BAND-NOT-COMPARABLE` and `lib/summary.ts:274-275` gates `typicalRange`/`source` on `!bandNotComparable`. Update the worklist so this does not reappear as a work item.

## 3. WHAT IS UNSAFE — where a well-meaning implementer satisfies the letter and destroys the property

**(A) Item A ships a user-visible clinical assertion with no measurable accuracy. This is the 80%/27.4% failure, reproduced exactly.** The "Marked high on your report" chip attributes a determination to the hospital. Its correctness depends entirely on whether the model transcribed a glyph or *induced* one by comparing the value to the range — the induction the prompt at Item A §2 tries to forbid. Item A's Lock 1 only proves that a **null** flag never yields a `Marked …` chip. Nothing can prove a **non-null** flag is genuine, because Item A's own Lock 7 correctly forbids synthesising `printedFlagRaw` from `is_abnormal`, and notes both corpora's flags are direction-free anyway. So the plan renders a clinical claim whose false-positive rate is, by construction, unmeasurable — and a hallucinated ↑ is *worse* than today's derived chip, because it launders our inference as the lab's determination. **Guardrail the spec must carry: land the schema field, the prompt, and `printedFlagDirection` DARK — captured, logged, never rendered. Rendering the `Marked …` chip is a separate, later item, gated on a hand-transcribed fixture of ≥50 rows read off page images with a measured false-positive rate. State the number before rendering.**

**(B) Tibetan cannot be policed by the existing gate, and the gate is *designed to fail* the moment Item G Tier 0 lands.** `validation/b1VerdictLeakage.test.ts:109-121` documents that the `directBo` tripwire "MUST fail on the first direct clinical string" because "the EN/ZH regular expressions cannot police future Tibetan prose". Item G Tier 0–1 ships `bo: reviewed(...)` on disclaimers and all 36 guard messages. An implementer optimising for green will delete or narrow that tripwire — one line, tests pass, and the entire clinical-copy gate silently stops covering the app's primary language. **Guardrail: the tripwire may be replaced only by Tibetan-specific `BANNED`/`CARD_BANNED` regex banks authored by the same medically-literate Tibetan reviewer, landed in the same commit. Removing the tripwire without replacement is a rejected diff, not a passing test.**

**(C) The `ALLOWED_CHIPS` allow-list becomes self-certifying in Tibetan.** `validation/b1VerdictLeakage.test.ts:78-95` asserts every chip is a member of a hand-written exact-string set. For EN/ZH that is a real gate because a reviewer reads both. Extend it to `bo` (Item G Tier 2 ships Tibetan chips) and the assertion becomes "the chip equals the string we put in the list" — tautological, in a script nobody on the team reads. **Guardrail: Tibetan chip strings enter `ALLOWED_CHIPS` only with an independent back-translation into EN recorded as a comment beside each entry, by a second reviewer.** Item A's Lock 5 has the same shape and the same fix.

**(D) Item F option (a) converts a confirm gate into a tap-through.** Making `ConfirmValues.tsx:24` unconditional on a 40-row Chinese panel produces 40 editable fields on a phone. The letter — "the confirm screen is not conditional on the patient's value" — is satisfied. The property — the user actually verifies the high-stakes numbers — is destroyed, and worse, `submit()` at `:41-49` re-grounds from every edited field, so a user scrolling past can now corrupt values they never looked at. **Guardrail: if option (a) is chosen, high-stakes rows must remain visually and structurally distinguished within the unconditional list on an *analyte-level* basis (`entry.highStakes`, never `classification`), and the spec must require a measured confirm-burden number (median fields per report on both corpora) before and after.**

**(E) Item D's R6-gold prediction is a pressure gradient in one direction, and Item D itself names the cheat.** Six rows (`wbc_count`, `rbc_count`, `hematocrit`, `urea`, `lymphocyte_abs`, `urine_ketones`) sit at `highStakes: false` against gold `true`. Flipping them takes 62.2% → ~86% in six one-word edits. Item D refuses this correctly and at length; `docs/superpowers/specs/2026-07-19-chinese-coverage.md:§3.1` refuses it independently. **The spec must carry that refusal as a hard constraint, not a recommendation: any diff to a `highStakes` field in `data/reference-labs.ts` in this cycle is rejected on sight unless accompanied by a cited clinical source.** Same for Item C: `absoluteLow`/`absoluteHigh` are R13's only net, and widening a bound is the cheapest way to make a negative-value test pass.

**(F) Item C's regex change trades a latent defect for a live one unless the signedness gate is in the same commit.** Item C verified this correctly: relaxing `lib/classify.ts:4` to accept `-` makes `structurallySuspicious` (`lib/guard.ts:56-64`) return `false` for negatives, so R5 stops firing, and the three qualitative dipstick entries plus urine specific gravity have `absoluteLow: null` so R13 cannot catch the fallout — a misread `-1.020` would newly classify as `low`. **Guardrail: the spec must state that the regex change and the signedness gate are one atomic commit, and must state `\d+` not `\d*` explicitly** (Item C is right that `parseValue('-')` returning `null` is the single test that catches the slip; `validation/real-corpus/sample.ts` carries `item_value: '-'` twelve times).

**(G) `chipFidelity.test.ts` is an independent oracle and items A and E both create pressure to teach it about flags.** Its header (`:29-38`) says it deliberately re-derives. Once Item A adds a glyph table, the cheapest way to make the oracle agree is to import that table. **Guardrail: `validation/chipFidelity.test.ts` and `validation/goldLabelGates.test.ts` are must-not-touch in this cycle. Any diff to them is rejected.** Item A says this; the spec must say it for all seven items.

**(H) `validation/silentAssertion.test.ts` will silently stop covering the new path.** Item A found this and it is the most easily missed item in the plan: the `asserted` detector keys on `/your report’s range/`, so a `Marked …` chip asserts a position that the no-silent-assertions invariant no longer sees. The test stays green while its coverage drops. Same class as (B). **Guardrail: widen the detector in the same commit that introduces any new position-asserting chip.**
